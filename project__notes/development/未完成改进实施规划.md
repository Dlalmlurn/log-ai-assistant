## 2. 实施顺序

### M0：保护当前基线

目标：先确认当前分支和测试入口可用，避免后续修改时难以判断回归来源。

任务：

- 保持 Docker-first 测试入口：`docker compose run --rm tester`。
- 修改前记录当前主要失败项；若 Docker 不可用，才用 `PYTHONPATH=. pytest -q` 作为 fallback。
- 不在本阶段调整业务逻辑。

验收：

- 能给出当前测试入口结果。
- 后续每个里程碑都能说明新增或更新了哪些测试。

### M1：P0 评分统一与版本化

目标：让代码、文档、前端和历史结果解释口径一致。

实现任务：

1. 新增评分策略配置，例如 `config/risk-scoring-v1.json`：
   - `scoring_version`
   - 风险等级阈值：`low 1-25`, `medium 26-50`, `high 51-75`, `critical 76-100`
   - 分项上限：规则强度 25、baseline 偏离 35、行为敏感度 20、事件关联度 10、反馈修正 10
   - reason code 到分项得分的版本化映射
2. 新增或抽出 `src/detection/scoring.py`：
   - 负责加载策略、裁剪分项上限、计算总分和等级。
   - `AnomalyEventBuilder` 只组装事件，不再硬编码阈值和 reason 分值。
3. 数据契约补齐：
   - `AnomalyEvent` 显式增加 `scoring_version`。
   - ClickHouse `anomaly_events` 增加 `scoring_version String DEFAULT ''`，保留 `model_version` 表示检测模型或规则模型版本。
   - 新增迁移脚本，例如 `sql/clickhouse/04_scoring_and_risk_migration.sql`。
4. 前端和 API 补齐：
   - 详情页展示评分版本。
   - TypeScript 类型增加 `scoring_version`。
5. 测试算例：
   - 覆盖 3 到 5 个典型场景：单纯非工作时间登录、账号接管、数据外传、维护窗口降权、baseline 低置信度。
   - 更新旧测试中 `90/70/40` 的断言。

验收：

- `src/detection/anomaly_builder.py` 不再直接持有等级阈值。
- 新事件写入 `scoring_version`。
- 所有高危候选逻辑仍以 `high/critical` 枚举判断，不依赖旧数字阈值。

### M2：P0 用户窗口化风险

目标：把单事件风险和用户风险排行拆开，避免长期历史事件造成风险膨胀。

实现任务：

1. API 语义：
   - 保留 `GET /api/v1/stats/users/risk`。
   - 增加 `window` 参数：`24h`, `7d`, `30d`, `custom`。
   - 默认窗口建议为 `7d`，页面可切换 24h/7d/30d。
2. 聚合语义：
   - 默认排除 `status = 'false_positive'`。
   - 计算 `event_risk_max`、`high_risk_count`、`critical_count`。
   - 增加衰减风险分，例如按半衰期 7 天对 `risk_score` 加权求和。
   - `30d` 只用于趋势，不等同于永久累计风险。
3. 模型和前端：
   - `UserRiskStats` 增加 `window`, `active_risk_score`, `decayed_risk_score`, `false_positive_excluded_count`。
   - 前端风险排行增加窗口切换和衰减分展示。
4. 测试：
   - 误报事件不进入有效风险。
   - 旧事件在衰减分中低于新事件。
   - 未传 `window` 时使用默认窗口。

验收：

- 用户风险排行不再暗示“永久累计风险”。
- API 返回能同时解释窗口、事件数和风险分。

### M3：P1 验收指标补齐

目标：从“能检出”推进到“检得准”。

实现任务：

1. `acceptance_scenario_rows` 补齐验收计算需要的字段：
   - 日志侧：`injected_label`, `scenario_type`, `attack_chain_id`, `step_index`。
   - 异常侧：`risk_level`, `attack_type`, `reason_codes`, `related_event_ids`。
2. 新增指标：
   - `precision_high_risk`
   - `recall_attack_event`
   - `attack_type_confusion_matrix`
   - `risk_level_accuracy`
3. 报告结构：
   - 简单数值仍写入 `acceptance_metrics`。
   - 混淆矩阵、等级准确率明细写入 metric `details`。
4. 阈值配置：
   - 在 `config/acceptance-thresholds-v1.json` 增加 precision/recall 阈值。
   - 先以可达、可解释的阈值进入 CI，后续再收紧。
5. 消融对比：
   - 第一轮先支持报告维度标识：`policy_version`, `baseline_model_version`, `scoring_version`。
   - 后续再增加自动双跑 baseline-off / feedback-off。

验收：

- 验收报告能回答“报出的 high/critical 有多少是真的”。
- 能按攻击类型看到混淆关系，而不只是总体检出率。

### M4：P2 URL 模板化与资源指纹

目标：减少动态 URL 造成的资源基数爆炸，并为 baseline、规则和反馈提供稳定资源键。

第一轮实现策略：

- 不急于扩表，先把归一化结果写入 `NormalizedLog.attrs`：
  - `url_template`
  - `resource_fingerprint`
  - `resource_normalization_version`
- 当解析层、baseline 和检测都稳定使用后，再评估是否新增 ClickHouse 独立列。

实现任务：

1. 新增 `src/parser/url_normalization.py`：
   - `/user/123/detail` -> `/user/{id}/detail`
   - UUID、长 hex、纯数字 ID、时间戳、常见 token/query 参数归一化。
   - 对模板做稳定 hash 作为 `resource_fingerprint`。
2. 在 `normalize_raw_record` 中对 `resource` 和 `object_id` 尝试归一化。
3. baseline 统计优先使用模板或指纹，保留原始资源用于证据展示。
4. 敏感资源关键词匹配优先基于模板 path，不使用 query token。
5. 测试：
   - 同类动态路径归为同一模板。
   - 不同业务路径不会过度合并。
   - query 中敏感 token 不进入 fingerprint。

验收：

- 动态 ID 不再把同类接口拆成大量不同资源。
- 异常证据仍能展示原始 `resource`，便于人工排查。

### M5：P2 detector 状态持久化

目标：明确并减少 detector 重启导致的短窗口检测断点。

实现任务：

- 先给当前内存窗口增加启动说明和健康指标，明确窗口重建所需时间。
- 评估两条实现路径：
  - 查询 ClickHouse 最近 N 分钟日志重建窗口。
  - 新增 detector state 表保存滑动窗口摘要。
- 优先选择“启动时从 ClickHouse 重建最近窗口”，避免引入新的强状态表。

验收：

- detector 重启后横向移动、失败登录等短窗口规则不会完全从零开始。
- 仍保留幂等事件 ID，避免重建窗口导致重复异常。

## 5. 风险与边界

- 评分阈值从 `90/70/40` 调整到 `76/51/26` 会改变 high/critical 数量，必须同步更新测试和演示话术。
- `scoring_version` 不应替代 `model_version`；前者解释分数口径，后者解释检测模型或规则版本。
- 窗口化用户风险不应改写历史异常事件，只改变聚合和展示方式。
- 误报剔除依赖事件状态，后续人工确认入口应把 `false_positive` 状态纳入闭环。
- URL 归一化第一轮写入 `attrs`，避免过早扩表；如果后续查询性能或 API 过滤需要，再独立列化。
